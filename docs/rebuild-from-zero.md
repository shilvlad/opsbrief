# OpsBrief: восстановление с нуля

Сервер OpsBrief хранит **только последнюю сводку** в SQLite. Это восстановление намеренно **не переносит старую БД**: после запуска отправь свежую сводку с Mac командой `python -m opsbrief.daily run --upload`. Не отключай действующий сервер до проверки полного цикла.

## Обязательные условия

- Новый VPS: **чистая Ubuntu 24.04**, доступ по SSH ключу под пользователем с **беспарольным sudo**.
- DNS `OPSBRIEF_DOMAIN` уже указывает на публичный IP **нового** VPS. Для перевода существующего домена это означает окно переключения; до него можно тестировать на отдельном тестовом поддомене.
- Доступные извне TCP 80 и 443 для Let's Encrypt / webhook, SSH от GitHub Actions runner для развёртывания (или self-hosted runner/VPN).
- Оригинальный ID приватного навыка Алисы; токен отправки и webhook secret должны совпадать со значениями в настройках Mac и Яндекс Диалогов либо быть заменены одновременно.
- В GitHub создать environment **opsbrief-recovery**, включить required reviewers для ручного подтверждения деплоя. Не ставить туда production-секреты до проверки доступов к workflow.

## Настройки GitHub environment `opsbrief-recovery`

**Secrets**:
- `DEPLOY_HOST` — публичный адрес нового VPS; не домен приложения.
- `DEPLOY_USER` — SSH-пользователь с `sudo -n`.
- `DEPLOY_SSH_KEY` — приватный SSH-ключ для подключения к новому VPS.
- `DEPLOY_HOST_KEY` — проверенная строка SSH known_hosts для нового VPS. Получить `ssh-keyscan` можно для черновика, **сверить отпечаток с консолью провайдера** до помещения в секрет.
- `OPSBRIEF_UPLOAD_TOKEN` — длинный секрет загрузки.
- `OPSBRIEF_WEBHOOK_SECRET` — отдельный длинный секрет webhook.
- `OPSBRIEF_ALICE_SKILL_ID` — ID навыка.
- `OPSBRIEF_ALICE_ALLOWED_USER_IDS` — необязательный список разрешённых user_id.

**Variables**:
- `OPSBRIEF_DOMAIN` — FQDN, например тестовый `opsbrief-staging.example.com` (без `https://`).
- `LETSENCRYPT_EMAIL` — email для уведомлений о сертификате.

**Безопасность:** не записывай приватные ключи или секреты в Git. Не используй для deploy ежедневный root SSH-ключ. Установи отдельный deploy-ключ и ограничь его использование. Репозиторий публичный: доступ к environment и правам на запуск workflow должен быть минимальным.

## Как запустить

1. Зафиксировать текущую конфигурацию домена/навыка и сохранить секреты **вне старого VPS**.
2. Подготовить чистый VPS с SSH и доступным sudo; создать DNS для тестового имени и открыть 80/443.
3. GitHub → Actions → **Rebuild OpsBrief VPS** → Run workflow. Job `verify` выполняет тесты, проверку Python, Bash и Docker build. Job `deploy` требует разрешения environment и затем выполняет bootstrap + HTTPS.
4. Дождаться успешной проверки `https://<DOMAIN>/health`. Проверить сертификат, выполнить тестовую загрузку сводки с Mac и тест запроса из Яндекс Диалогов (для тестового поддомена временно изменить webhook URL).
5. Только после фактической проверки восстановленного экземпляра и сохранения секретов отключать старый VPS.

## Ограничения

- Этот сценарий **не воспроизводит настройки провайдера**, DNS-записи, доступы к VPS, настройки Mac и Яндекс Диалогов; они должны быть настроены отдельно.
- Nginx отключает access log для `/alice/webhook/`, чтобы не записывать секрет URL.
- Пакеты Ubuntu устанавливаются из репозиториев ОС; точные версии пакетов и Docker base image не зафиксированы. Это повторяемое развёртывание, а не побитово идентичная сборка.
- Повторный прогон обновит checkout приложения и контейнеры; SQLite volume сохраняется. На **существующий** VPS с чужими приложениями это не рассчитано.
- На новой машине сначала протестируй восстановление, не отключая старый сервис. Временное переключение DNS может влиять на настоящий webhook.
- Нет резервного копирования истории сводок и нет гарантии сохранения state. Восстановление свежих данных потребует Mac.
