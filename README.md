# OpsBrief

Локальный помощник руководителя инженерной команды.

**Первый этап готов: автономный отчёт с расчётами.** Интеграции Jira,
история снимков, автоматическое расписание и Алиса пока находятся в плане развития.
Отдельно доступна экспериментальная ежедневная сводка macOS Calendar с Ollama/Qwen.
Демо работает без сети, модели и дополнительных Python-библиотек.

## Запуск на Mac

Нужен Python 3.11 или новее. Проверь: `python3 --version`.

```bash
git clone https://github.com/shilvlad/opsbrief.git
cd opsbrief
python3 -m opsbrief --input examples/demo.json --as-of 2026-10-19
open reports/weekly.html
```

Фиксированная дата нужна для воспроизводимого демо. Все сотрудники и задачи
вымышлены. Для текущих данных убери `--as-of`: будет использована локальная дата.
Отчёты HTML и JSON сохраняются в `reports/`, исключённой из Git.

## Что показывает отчёт

- Доступные часы после вычета отсутствий, встреч, сопровождения и резерва.
- Объём явно выбранных на неделю незавершённых задач и превышение доступных часов.
- Задачи без оценок или исполнителя, просрочки и зависимости.
- Дату исходных данных и их возраст.

В демо у DevOps 20 доступных часов и 24 часа задач — перегрузка на 4 часа.
У DBA 16 доступных часов, 8 часов оценённых задач и одна задача без оценки:
это **не означает**, что у DBA свободны оставшиеся 8 часов.
Закрытые задачи и бэклог не входят в недельную загрузку.

Это расчёт фактов, а не готовая AI-рекомендация. Назначения и сроки не меняются.
Программа принимает подготовленный JSON, а не произвольную выгрузку Jira.
Формат описан в [docs/input.md](docs/input.md). Рабочие данные храни в `data/` или `local/`.

## Разработка

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q opsbrief
```

Дальше: Jira API → история SQLite → расписание → приватный навык Алисы.
Расчёты выполняет код; модель будет формировать предложения со ссылками на задачи.
Алиса потребует отдельной разрешённой голосовой сводки: её текст передаётся Яндексу.

Лицензия Apache-2.0. В публичный репозиторий не добавляем корпоративные данные,
токены, реальные внутренние адреса или сформированные рабочие отчёты.


## Ежедневная сводка календаря macOS (MVP)

Нужны macOS с приложением «Календарь», Python 3.11+ и инструменты Swift
(установленные Xcode Command Line Tools: `xcode-select --install`).
При первом запуске разреши терминалу доступ к календарям в настройках
macOS «Конфиденциальность и безопасность → Календари».

```bash
# Выведет ID, название и источник всех доступных календарей:
python3 -m opsbrief.daily calendars

# Скопируй нужные идентификаторы из результата:
python3 -m opsbrief.daily calendars --select "ID_КАЛЕНДАРЯ_1" "ID_КАЛЕНДАРЯ_2"

# Первый запуск без AI: проверяем чтение реальных событий
python3 -m opsbrief.daily run --no-ai
cat reports/daily-$(date +%F).md

# Для анализа установи Ollama, загрузи модель и запусти обычный отчёт:
ollama pull qwen3:8b
python3 -m opsbrief.daily run
```

Для другой даты: `python3 -m opsbrief.daily run --date 2026-10-21`.
Для другой модели: `--model ИМЯ_МОДЕЛИ`.
Отчёты сохраняются в `reports/daily-YYYY-MM-DD.md` и `.json`.
Если Ollama недоступен, создаётся фактическая сводка без рекомендаций.
Модель выгружается из памяти после запроса; сервер Ollama может оставаться активным.

Выбор календарей сохраняется только локально в
`local/calendars.json` (эта папка исключена из Git).
Система не предполагает фиксированных рабочих часов. Свободными окнами
считаются только промежутки между встречами; интервалы до первой и после
последней встречи не оцениваются. События на весь день перечисляются,
но не считаются занятостью по часам. Пересекающиеся встречи учитываются
без двойного подсчёта. Важность встреч Qwen может лишь предполагать.
Отчёты и календарные сведения не отправляются на VPS или Яндексу.

Пока это MVP: сбор с настоящего календаря и работа Swift-компонента
требуют проверки на реальной macOS; выполнение на Mac разработчиком
не подтверждено.

## Интерпретация ежедневного отчёта

События длительностью от трёх часов показываются отдельно как продолжительные
блоки занятости. Это эвристическая категория по длительности, а не утверждение
об их назначении или возможности переноса. Пересекающиеся события выводятся
отдельно, но время пересечения учитывается только один раз. Qwen получает
инструкцию не выдумывать ссылки, повестку и свободное время; предполагаемая
важность встреч не считается фактом.

## Сервер для навыка Алисы (начальный MVP)

В репозитории: `server/app.py`, `server/Dockerfile`, `compose.yaml` и
`opsbrief/voice_upload.py`. На VPS нужны Docker Compose, внешний HTTPS
reverse proxy (например, nginx) и домен. Контейнер слушает только
`127.0.0.1:8080`, поэтому нельзя указывать публичный IP как адрес webhook
без настройки HTTPS.

На VPS создай `.env` из `.env.example`. Заполни секреты
`OPSBRIEF_UPLOAD_TOKEN` и `OPSBRIEF_WEBHOOK_SECRET` двумя разными
случайными длинными значениями. Пример генерации:
`python3 -c "import secrets; print(secrets.token_urlsafe(48))"`.
Укажи `OPSBRIEF_ALICE_SKILL_ID` после создания навыка.

```bash
docker compose up -d --build
curl http://127.0.0.1:8080/health
```

HTTPS proxy перенаправляет `/api/v1/brief` и `/alice/webhook/...`
на `http://127.0.0.1:8080`. В Яндекс Диалогах в поле Webhook URL укажи
`https://ТВОЙ-ДОМЕН/alice/webhook/ЗНАЧЕНИЕ_OPSBRIEF_WEBHOOK_SECRET`.
Приватный навык создаётся отдельно в консоли Яндекс Диалогов.

### Передача данных с Mac

Пока отправка намеренно **ручная и только обезличенная**. Создай локальный
файл `local/voice.json` следующего вида (данные условные):

```json
{
  "date": "2026-10-21",
  "timezone": "Europe/Moscow",
  "meetings": ["В 13:30 рабочая встреча", "В 17:30 ещё одна встреча"],
  "recommendations": ["Уточнить вопросы к первой встрече"]
}
```

После проверки, что там нет защищённых корпоративных сведений:

```bash
export OPSBRIEF_API_URL=https://ТВОЙ-ДОМЕН
export OPSBRIEF_UPLOAD_TOKEN=ТОТ_ЖЕ_СЕКРЕТ_ЧТО_НА_VPS
python -m opsbrief.voice_upload --file local/voice.json
```

Секреты не сохраняй в истории команд или Git. В текущем прототипе webhook
содержит секрет в URL и сверяет идентификатор навыка, но **не имеет
полноценной OAuth-авторизации или криптографической проверки происхождения
запроса от Яндекса**. Не отправляй на этот сервер подробные рабочие встречи,
задачи, персональные или конфиденциальные сведения. Для них сначала
потребуется OAuth 2.0 и проверка прав пользователя. Автоматическая
публикация необработанных отчётов намеренно не реализована.
